# 技术落地可行性方案

作品：电厂工单推送审核智能体（田贵恒，个人参赛）

> 本文是落地方案，不是落地结果。目前系统只在虚构的模拟工单上运行过，所有效果数字都对照模拟审核规则，不代表真实电厂效果。

## 一、可行性结论

| 方面 | 现状 | 判断 |
|---|---|---|
| 技术 | 完整原型已运行：工单理解、评分、分流、openJiuwen 单智能体与多智能体团队、人工审核、反馈学习、评测脚本；60 个后端测试通过 | 核心技术路线已验证可行 |
| 数据 | 只用模拟工单；真实工单的叫法、写法分布未知 | 主要不确定性，需要试点期用真实历史工单回放验证 |
| 安全合规 | 智能体只读、证据留痕、人工批准；大模型可换成厂内部署 | 设计上满足“可审计、不越权、数据可不出厂” |
| 成本 | 只有被分流的推送调用智能体；系统本体是单进程 + SQLite | 硬件和调用成本可控，具体取决于模型部署方式 |
| 组织 | 需要专工参与盲评和试点审核 | 需要电厂配合，是落地的前提 |

## 二、部署方案

### 网络位置

工单（缺陷 / 隐患记录）属于管理信息类数据，系统部署在厂内**管理信息大区**，只从缺陷管理系统读取工单文本，**不连接 DCS 等生产控制系统**，不向任何系统写入控制指令，符合《电力监控系统安全防护规定》中生产控制大区与管理信息大区分区的要求。

### 部署形态

| 形态 | 大模型 | 适用 |
|---|---|---|
| A. 厂内全本地 | 在厂内推理服务器部署开源模型（如通义千问、DeepSeek 开源版本），通过 Ollama、vLLM 等提供 OpenAI 兼容接口 | 工单不出厂，正式试点首选 |
| B. 集团私有云 | 集团统一部署的大模型服务 | 多个电厂共用，降低单厂成本 |
| C. 公有云 API | DeepSeek 等公有云 API | 仅用于脱敏数据或演示（当前原型采用此方式） |

切换只需修改配置（`LLM_BASE_URL`、`LLM_MODEL` 等），代码不变。三种形态下，大模型不可用时系统都会自动退回规则 + TF-IDF，推送照常进行，智能体调查显示为失败、由人工审核。

### 系统本体

- 后端为单个 FastAPI 进程，数据库为 SQLite，普通服务器即可运行；
- 多用户、多机组规模扩大后，可把存储换成 PostgreSQL（作者毕设的原系统即基于 PostgreSQL），接口层不变；
- 前端为静态文件，由后端直接提供，浏览器访问，无需安装客户端。

## 三、系统对接

| 对接对象 | 方式 | 说明 |
|---|---|---|
| 缺陷管理系统（MIS / EAM） | 只读拉取新工单（接口或数据库视图），调用本系统 `POST /predict` | 需要字段映射：标题、内容、机组、等级、设备类型、设备编码 |
| 人员与岗位 | 导入岗位、负责机组和专业 | 对应系统中的用户与画像基础兴趣 |
| 推送通道 | 本系统给出“推给谁”，由原有通道（企业微信、短信或缺陷系统自身的待办）发送 | 本系统不替代消息平台 |
| 推送规程 | 把电厂成文的岗位职责表整理进 `core/policy.py` 对应的结构 | 智能体与模拟审核都以此为依据 |
| 部件知识库 | 用电厂的设备台账、KKS 编码补充 `components.json` | 每条需人工审定后才进入规则词典 |

## 四、试点实施计划

| 阶段 | 内容 | 产出 | 进入下一阶段的条件 |
|---|---|---|---|
| 0. 离线准备 | 专工盲评（`专工盲评表.xlsx`，47 条模拟难例）；收集电厂岗位职责表和设备台账 | 专工与系统的一致程度；专工之间的一致程度；修订后的推送规程 | 系统在盲评中与专工多数意见的一致程度接近专工之间的一致程度 |
| 1. 历史回放 | 取一个机组若干月的脱敏历史工单，离线跑完整流程，与当时的实际分发对比 | 漏推、误推统计；真实工单中的叫法缺口（词表外新词） | 漏推率明显低于现有分发方式；无严重误判 |
| 2. 影子运行 | 系统实时给出建议但不推送，专工照原流程工作，每周比对 | 智能体建议与人工决定的差异清单 | 专工认可建议质量 |
| 3. 辅助运行 | 在一个机组、一个专业启用：规则直接推送，需重点审核的工单由按岗位调查预审、人工确认；疑似紧急由值班人员确认 | 审核时长、漏推数、专工满意度 | 指标稳定 |
| 4. 推广 | 扩展到全部机组和专业；按岗位拟合权重 | — | — |

### 评估指标

- **漏推数**（应推未推）和**误推数**（不应推却推了），以专工判断为准；
- 每条重点审核推送的人工处理时间；
- 智能体建议被人工采纳的比例，以及“需人工判断”的比例；
- 专工之间的一致程度（kappa），作为系统可达到的上限参照。

## 五、资源与成本

| 项 | 估计 | 依据 |
|---|---|---|
| 需调用智能体的工单 | 模拟名单 12 / 24 / 48 人时，被标为重点审核的推送为 688 / 1352 / 2623 条（约 18%），涉及的工单始终是 320 条中的 185 条；按岗位调查只需调查这 185 条 | `scripts/scale_test.py`，模拟工单；真实比例需回放确定 |
| 调查时长 | 按岗位调查每条工单约 12 秒（紧急程度约 5 秒，各岗位并行约 7 秒），与人数无关；单智能体每人约 9 秒 | DeepSeek API、模拟工单实测 |
| 批量评分 | 48 人 × 320 条约 13 秒（每对约 0.84 毫秒），随人数线性增长 | 本机实测，大模型关闭 |
| 系统服务器 | 普通服务器即可 | 单进程 + SQLite |
| 本地大模型 | 需要推理服务器，配置取决于所选模型规模 | 形态 A；可先用集团私有云（形态 B）降低门槛 |
| 人力 | 试点阶段需 2–3 位专工参与盲评和影子运行比对 | — |

“规则先打分、智能体只处理被分流的推送”的设计让调用量随难例数量增长，而不是随工单总量增长。

## 六、风险与应对

| 风险 | 应对（已实现的标 ✓） |
|---|---|
| 大模型编造事实 | ✓ 证据必须来自本次调用过的工具，数字必须能在工具返回中找到；✓ 不满足时降级为“需人工判断” |
| 智能体越权 | ✓ 所有工具只读；✓ 智能体不修改分数和审核结论；✓ 学习结果只是建议，须人工批准 |
| 大模型服务中断 | ✓ 工单理解自动退回规则 + TF-IDF；✓ 智能体失败时由人工审核；推送不中断 |
| 真实工单叫法与模拟数据差异大 | ✓ 词表外新词进入候选列表，人工审定后加入词典；✓ 部件知识库可扩充；试点阶段 1 专门测量 |
| 推送规程本身不合理 | ✓ 盲评表“规程意见”页收集专工意见；规程是可修改的数据，不写死在模型里 |
| 复核智能体不起作用 | 串行团队中复核员 140 次只退回 1 次，已如实记录；✓ “推给谁”改由按岗位并行调查承担，串行团队只保留作对照 |
| 紧急程度误报或漏报 | ✓ 推送等级取误报为零的大模型等级复核；✓ 只有紧急程度智能体判紧急时转值班人员确认，不自动全员推送；评测中仍有 1 条真紧急两者都没判出，需值班规程兜底 |
| 专工之间判断本身不一致 | ✓ 计分脚本报告专工之间的一致程度，避免把专工分歧算作系统错误 |
| openJiuwen 处于早期版本（0.1.x） | ✓ 引擎可切换，未安装或出错时可用内置循环；✓ 已修复连续调用时的事件循环问题并有回归测试 |
| 数据外泄 | ✓ 可全本地部署；✓ 公有云 API 只用于模拟或脱敏数据 |

## 七、可迁移性

“规则先打分 → 分流难例 → 只读工具调查 + 证据护栏 → 人工批准”的模式不依赖电厂特有的算法，只需替换推送规程、部件知识库和工单字段映射，即可迁移到电网、化工、轨道交通等需要把运维工单分发给对口人员的场景。

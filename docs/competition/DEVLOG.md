## 2026-10-27 环境与大模型接入

- 统一主线为 Vue 3 + FastAPI + SQLite，旧 React + PostgreSQL 版归档到 `_legacy/`。
- 新建 `.demo-venv` 与 `setup_venv.bat`：原 `.local-deps` 的 pydantic-core 与本机 Python 版本不匹配；固定版本在 Python 3.14 上无法编译时改装最新二进制包。
- 接入大模型工单理解（`core/llm.py`），选用 DeepSeek `deepseek-flash`、关闭思考模式（`deepseek-chat` 已于 2026-07-24 下线）。约束：标签代码白名单、结论须引用原文、等级只升不降、新词只进候选。321 条模拟工单全部分析成功，单条中位约 1.5 秒，未出现编造代码。
- **问题**：设备编号、型号被当成新词，78% 的工单被标为重点审核。**修复**：过滤编号和长短语，新词不再触发重点审核，比例降到 9%。

## 2026-10-27 画像、相似工单、反馈学习

- 相似工单检索（`core/similar.py`）、重点审核分流、AI 推送解读。
- **问题**：画像按最大值归一化，两次点击就把兴趣拉到 1.0。**修复**：改为饱和函数 1 − e^(−w/8)。
- **问题**：“相似工单被修改”提示泛滥。**修复**：只有本条分数与人工修正分相差超过 0.15 时才提示。
- 反馈学习（`core/learning.py`）：权重拟合、画像调整建议、一致性指标；所有调整须人工批准。
- 模拟审核员（`scripts/simulate_review.py`）：按岗位规则审核，用来在没有真实审核数据时跑通学习闭环。

## 2026-10-27 评分 v2 与岗位权重

- **问题**：负责机组的所有工单都带约 0.28 的岗位底分，无关工单也被当成“个性化推送”。**修复**：评分 v2，设备对口或紧急才拿满岗位分。
- **问题**：一套全局权重不适合所有岗位。**修复**：按岗位存储权重，拟合时按岗位分别计算。
- 结果（对照模拟审核规则，非真实效果）：汽轮机专工平均分差 0.129 → 0.056，推送判断一致率 71% → 100%。

## 2026-10-27 审核助手智能体（内置引擎）

- `core/agent.py`：模型自主调用 7 个只读工具调查重点审核工单，最多 8 步，提交结论时由 `validate_conclusion` 校验证据。
- **智能体发现的系统缺陷**：早期 6 次调查中有 4 次指出触发重点审核的相似工单修改来自另一个岗位。**修复**：重点审核只看本人的审核结论（汽轮机专工重点审核 52 → 23 条）。
- **问题**：证据数字核实过严，7 条误报。**修复**：允许四舍五入、跨工具引用，跳过系统阈值常量；每步保存工具原始返回供核对。
- DeepSeek 实测 41 次（汽轮机专工，对照模拟审核规则）：40 次明确结论与规则一致，建议分平均误差 0.027（模型原分 0.061），1 次自相矛盾被自动降级。
- 前端批量预审：可选择条数、显示进度、可中途停止。

## 2026-10-28 迁移到 openJiuwen 与参赛整理

- 新增 `core/agent_openjiuwen.py`：审核助手改由 openJiuwen agent-core 的 `ReActAgent` 驱动。7 个工具与提交结论工具注册为 openJiuwen `LocalFunction`；`AFTER_MODEL_CALL` 回调记录每步推理；工具预算、结论护栏与内置引擎共用。
- 引擎选择：`AGENT_ENGINE=openjiuwen|builtin`，未设置时装了 openjiuwen 就用它；`/llm/status` 返回当前引擎；界面在结论下方标注“openJiuwen ReActAgent 驱动”。
- openjiuwen 需要 Python 3.11–3.13：新增 `setup_openjiuwen.bat`（建 `.jiuwen-venv`）与 `requirements-openjiuwen.txt`；`start_demo.bat` 优先使用该环境。
- 新增 `tests/test_agent_openjiuwen.py`：用本地假 OpenAI 兼容服务驱动 ReActAgent 完整走一轮调查，验证工具调用、证据护栏、步数预算、DeepSeek 关闭思考参数。
- 合规材料：Apache-2.0 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md`、数据来源说明、既有基础与新增贡献说明；`.gitignore` 排除密钥、虚拟环境、论文文件；初始化 Git 仓库。

## 2026-10-31 openJiuwen 引擎真实模型实测与修复

- 首次用真实 DeepSeek（`deepseek-flash`，关闭思考）跑 openJiuwen 引擎：汽轮机专工的前 8 条重点审核工单，两个引擎各跑一遍（数据库副本，不影响演示库）。
- **问题**：openJiuwen 引擎成功、失败交替出现（8 次成功 4 次），失败的都在第 0 步报 `RuntimeError: Event loop is closed`。原因：每次调查都用 `asyncio.run` 新建并关闭事件循环，而 openJiuwen 会缓存异步 HTTP 客户端，这个客户端绑定在已关闭的循环上。批量预审、连续点击都会触发。原有测试每个应用只跑一轮，所以没发现。**修复**：所有 openJiuwen 调用改在一个常驻后台事件循环上执行（`_run_coro`）；新增测试 `test_consecutive_runs_in_one_app`（同一应用连续调查 3 次）。
- 修复后结果（对照模拟审核规则、数据为模拟工单，非真实效果）：

  | 引擎 | 成功 | 明确结论与规则一致 | 建议分平均误差（模型原分） | 平均步数 | 耗时中位 |
  |---|---|---|---|---|---|
  | openJiuwen ReActAgent | 8/8 | 8/8 | 0.023（0.045） | 6.6 | 8.9 秒 |
  | 内置循环 | 8/8 | 8/8 | 0.023（0.045） | 6.9 | 8.2 秒 |

  两个引擎对 8 条工单的建议（推送 / 不推送）完全一致。样本只有 8 条，只能说明两个引擎表现相当，不足以区分优劣。
- **观察**：openJiuwen 会严格按工具 schema 校验参数。模型 3 次给 `recent_unit_orders` 多传了 schema 里没有的 `unit_no`，被拒后自行改正并继续调查，不影响结论；内置引擎遇到这种情况会直接忽略多余参数。暂未修改。

# 需求与场景分析

作品：电厂工单推送审核智能体（田贵恒，个人参赛）

> 说明：本文的业务流程与痛点基于作者毕业设计期间对电厂工单推送问题的研究和通用行业常识整理，尚未经过实地调研验证。文中所有示例工单均为虚构，效果数字均对照模拟审核规则、数据为模拟工单。

## 一、业务背景

火电厂的设备缺陷、隐患通过工单记录：运行或巡检人员发现问题后录入缺陷管理系统，再由值班人员或系统把工单分发给对口的专业技术人员（专工）跟进。分发是缺陷从“发现”到“处理”的第一道关口：

- **漏推**：关键缺陷没有到对口专工手里，可能错过处理窗口，有安全代价；
- **错推、多推**：专工被大量无关工单淹没，真正重要的工单反而被忽略。

常见做法是按“设备类型字段 + 机组”粗放分发，或用规则 / 关键词评分。它们能处理大多数工单，但总有一批工单规则判断不准。

## 二、用户与角色

| 角色 | 关心什么 | 在系统中做什么 |
|---|---|---|
| 运维专工（汽轮机、电气、锅炉等） | 只看和自己相关的工单，不漏掉本专业、本机组的问题 | 接收推送；查看推送理由与智能体的调查结论 |
| 值班审核人员 / 工单分发人员 | 快速、准确地分发；拿不准的工单有依据可查 | 对推送确认或修改并填写理由；批准权重、画像和词典调整 |
| 生产管理人员 | 推送可追溯、可复盘；审核经验能沉淀 | 查看一致性指标、调整历史、智能体调查记录 |

演示中使用三个虚构岗位：汽轮机专工、电气专工、锅炉专工，都负责 #1 机组。

## 三、现状流程与痛点

现状（简化）：缺陷录入 → 按设备类型字段分发给专工 → 专工自行判断是否相关 → 不相关的工单被忽略或人工转发。

| 痛点 | 具体表现（示例均为虚构） | 后果 |
|---|---|---|
| 描述口语化，同一设备多种叫法 | “3 号瓦轴振”“低加水位高”“定冷水流量低”并不直接出现“汽轮机”“发电机”等词 | 规则抽不到设备，分数偏低 → 漏推 |
| 设备词只作地点 | “汽机房屋顶漏雨”“主变区域照明损坏” | 规则看到设备词就推 → 误推 |
| 设备类型字段填错 | 正文讲汽轮机轴振，字段却填“发电机” | 按字段分发直接推错人 |
| 填报等级偏低 | 正文描述已危及设备或人身安全，等级仍填“一般” | 应知晓的人没有收到 |
| 拿不准的推送只能人工逐条核对 | 依据不留痕，经验难沉淀 | 审核压力大，老师傅经验无法复用 |
| 推送系统本身的问题难发现 | 某类工单长期被错判，没人察觉 | 错误持续存在 |

## 四、需求

### 功能需求

| 编号 | 需求 | 对应实现 |
|---|---|---|
| F1 | 从口语化工单中识别设备、故障、等级，能处理俗称和部件名 | 规则词典 + TF-IDF + 大模型理解；设备—部件知识库（70 个部件、180 个叫法） |
| F2 | 按岗位、机组、个人兴趣给每条推送打分，并说明理由 | 四维评分 v2（设备 / 行为 / 岗位 / 厂家），岗位专属权重 |
| F3 | 自动找出“拿不准”的推送，并说明为什么拿不准 | 分流：灰区分数、大模型上调等级、新设备、未识别设备、字段与原文不符、设备词只作地点、相似工单曾被本人修改 |
| F4 | 对拿不准的推送做调查，给出建议和逐条可核对的证据 | openJiuwen 审核智能体：9 个只读工具，证据护栏 |
| F5 | 判断一条工单还应该推给谁（漏推）、不该推给谁（多推） | openJiuwen 多智能体团队：理解 → 调查 → 复核；漏推 / 多推提示 |
| F6 | 人工确认或修改推送，保留原始评分和全部历史 | 审核表单；反馈只追加、不覆盖 |
| F7 | 用人工审核结果改进推送，但改动须人工批准 | 权重拟合、画像建议、词表外新词候选；批准后生效 |
| F8 | 批量预审，减少逐条点击 | “助手预审重点工单”按钮 |
| F9 | 能评测效果，并能请专工独立检验 | 困难工单集 + 两批留出集；专工盲评表与计分脚本 |

### 非功能需求

| 方面 | 要求 | 设计 |
|---|---|---|
| 可审计 | 每条建议的依据可追溯、可复核 | 证据必须来自本次调用过的工具，数字必须能在工具返回中找到；完整调查过程留档 |
| 安全 | 智能体不能直接改变推送结果 | 所有工具只读；智能体不修改分数和审核结论；学习结果只是建议 |
| 可靠 | 大模型不可用时系统照常工作 | 大模型失败自动退回规则 + TF-IDF；智能体失败或证据不足 → “需人工判断” |
| 数据合规 | 工单数据可不出厂 | 大模型通过 OpenAI 兼容接口接入，可换成厂内部署的本地模型 |
| 成本与时延 | 算力花在难例上 | 只有被分流的推送才调用智能体；单智能体约 9 秒、团队约 25 秒一条（DeepSeek，模拟工单实测） |
| 可替换 | 不绑定单一模型或框架实现 | 模型可换（DeepSeek / 通义千问 / Ollama）；智能体引擎可切换（openJiuwen 单智能体 / 团队 / 内置循环） |

## 五、典型场景

### 场景 1：俗称和部件名导致的漏推

虚构工单“#1机3号瓦轴振波动”，设备类型字段误填为“发电机”。规则按字段打分，汽轮机专工只得 0.22，不会推送。分流发现“字段与原文不符”，标为需重点审核。多智能体团队调查后：理解员确认实际设备是汽轮机轴系，调查员建议推送（建议分 0.78），复核员第一次提出质疑、退回修改后同意；同时提示“汽轮机专工可能漏推”“电气专工可能多推”。审核员按建议预填表单，确认后保存。（界面截图见《界面原型与示意》。）

### 场景 2：设备词只作地点导致的误推

虚构工单“汽轮机厂房屋面彩钢板漏雨”。规则看到“汽轮机”给汽轮机专工 0.77 分，会推送。分流提示“设备词只出现在地点描述中”；单智能体查推送规程（厂房建筑问题即使发生在设备厂房内，也不推给该设备专工）后建议不推送，建议分 0.2。

### 场景 3：填报等级偏低

虚构工单“#1机发电机出口封母冒烟”，填报等级为“一般”，但冒烟已属需要立即处理的紧急情况。系统的大模型理解只能在引用原文片段的前提下上调等级（只升不降）；按推送规程，本机组的紧急事件各专业都需知晓，即使不是本专业设备。

### 场景 4：用审核经验改进推送

审核员确认或修改一批推送后，在“学习与评估”页看到：模型与人工判断的一致程度、按岗位拟合的建议权重、画像调整建议和词表外新词。审核员逐项批准，批准后用于下一轮评分。演示中，智能体还在调查中指出“触发重点审核的相似工单修改来自其他岗位”，据此修正分流规则后，汽轮机专工的重点审核从 52 条降到 23 条（模拟数据）。

## 六、需求边界（本作品不做的）

- 不替代缺陷管理系统，不处理缺陷的消缺、验收流程，只负责“推给谁”的判断与审核；
- 不连接 DCS 等生产控制系统，只读取工单文本；
- 智能体不做最终决定，推送结果由人确认；
- 目前没有真实电厂数据，所有效果只在模拟工单上、对照模拟审核规则验证过。
